Dynamo

One agent, one real checkout.
Three workflows. Everything below was measured.

A headless-agent script drives a real Chromium through a real HTTP storefront — filling in a form, tripping a validator, getting declined twice, retrying, and completing the order. The whole thing is recorded three different ways. Every image, video, frame count and byte total on this page is a real artifact from a real run.

1440×900 · 20 fps · Chromium (Playwright, headed) · 52.15 s · 1043 captured frames

  3. 3fix it, continue to payment

Two of those steps are failures the agent has to see in order to recover from — and the agent cannot see them, because it only reads the DOM. That is the entire argument for recording the screen.

Being straight about it: screenshots-only and Dynamo cost about the same in tokens (26,400 vs 31,900), because both sample on actions rather than on wall-clock time. Dynamo's advantage is not the token count — it is everything screenshots cannot produce at all: the video, the GIF, the click overlays, the timing manifest, and a recording that survives a crash.

Underlying metric

Frame count is the wrong number. Information per frame is the right one.

Each image set was decoded to a 64×64 RGB buffer and compared pixel-by-pixel with its predecessor. No similarity threshold is used: two samples of a still screen are bit-identical, so exact comparison is enough — and nothing here is a cutoff tuned to get the answer we wanted. The left column is not hypothetical — it is the literal stderr from a real run. A missing moov atom is not repairable for MP4; there is no index to rebuild from. That is exactly why Dynamo sends SIGINT to ffmpeg on every exit path, including when your agent's code raises.

Everything else an agent needs from a screen

Recording is one capability. An agent needs four more to actually work unattended.

Above covers recording, GIF export and the virtual display. Those get an agent a replay. What they cannot do is tell it what error the page showed, which pixels moved, or where the button is — and those are the questions an unattended agent actually asks. On a normal page you can get them from the DOM. On a canvas, a VNC session or a HiDPI display you cannot, and no operating system ships a headless tool for it. Each block below is a measured run against this same real storefront in the same real browser: dynamo capture, ocr, diff and som.

The honest part: under flat per-image pricing a snip saves nothing — 1,100 tokens either way, because the model is billed per image and the crop is still one image. Sized pricing tells the other story: 991 → 50 tokens. The crop's real win is not the price of this call — it is that a focused image is both cheaper to look at and measurably easier to read: confidence rose from 74.0% to 81.3% because Tesseract's page analysis no longer has to decide which part of a 1440×900 frame is the text.

This is the case no OS covers. macOS Live Text and the Windows Snipping Tool both exist, both are interactive overlays, and neither is reachable from a shell. The log above is painted to a <canvas>, so a scraper finds the empty string — the probe on the page proves it. OCR reads it locally for free in 0.66s and hands back word boxes, which is what lets you point back at the pixels you just read.

And it gets some things wrong, measurably. Against the page's own log, Tesseract returns:

truth   09:12:44.201Z issuer.acquirer DECLINED reason=do_not_honor response.code=05 response.text=Do not honor
ocr     09:12:44.201Z issuer.acquirer DECLINED reason=do_not_honor response.code=@5 response.text=Do not honor

truth   09:12:44.310Z gateway.txn terminal state=FAILED retryable=false attempt=3 of 3
ocr     09:12:44.3102 gateway. txn terminal state=FAILED retryable=false attempt=3 of 3

It reads O as 0, 1 as l, and a monospace underscore as a space. A character whitelist does not fix it and neither does any page-segmentation mode — both were tried. So Dynamo does not pretend the text is exact: it keeps the recognised characters verbatim for the report, and folds 2 of the 8 missed tokens back into matches at search time. An agent asking "is DO_NOT_HONOR on this screen" gets a yes; an agent pasting a transaction id into a ticket gets the characters that were actually there.

The red overlay is the deliverable. Changed pixels in red over a dimmed original is the artefact a reviewer actually looks at, and it is also something a vision model can describe in one sentence. The control matters as much as the finding: the same image compared against itself reports 0 changed pixels, so a non-zero result here is signal rather than noise. A diff that flags everything gets switched off within a week, and then it catches nothing — which is why --threshold and --min-changed-pct exist, and why both are reported in the result rather than hidden behind the verdict.

Why the model answers with a number. Ask a vision model "continue to payment" and it returns a coordinate by pattern-matching a description onto an image. It is wrong often enough to be useless, and wrong confidently. Set-of-Marks draws the boxes instead, so the model replies with an index — and a wrong answer is a wrong index, which is checkable, rather than a wrong coordinate, which is not. The boxes came from a live DOM query and the pixels from the display; the only step between them is the transform the surface reports (origin 0,85 — here the browser's own chrome, not a scale factor, is what moves the page off the origin). Note the two rows above: the box is in image pixels, the resolved click is in pointer pixels, and they differ by exactly that origin. Reporting only one of them is how an agent ends up clicking 85 pixels too low.

One rule worth stating. Grounding refuses any box with no area, because an element clipped by the viewport reports a zero-height rect, cannot be clicked, and would still get a mark drawn on it — inviting the model to pick an index that resolves to a point outside the button. On this page, 0 of 17 elements hit that case at the scroll position shown, and 0 after scrolling the action row into view. The numbers are small here because this viewport happens to fit the form; on a shorter window they are not, and the check is the difference between a reported failure and a click that lands on empty page.

This is measured, not asserted. A real browser at devicePixelRatio: 2 was opened, OCR read the button's label out of the resulting 2880×1600 image, and the page was clicked twice. The first click used that coordinate exactly as the agent saw it and missed by 136,173 pixels. The second normalised by the scale factor and hit the button. On a Retina MacBook or a 4K Windows display every screenshot-triggered action fails this way, and it fails quietly: the click lands on empty page space, so the agent sees no error and reports success. That is why the conversion lives in one place — Scale — and everything else in the harness asks it rather than guessing.

Note the two boxes above are not the same thing. OCR returns 140×23 — the glyphs. The button is 287×70. Reading pixels finds text; it does not find the control's border. That is precisely why element boxes come from the DOM or CDP and the harness only draws them.

When a model is genuinely needed

An open-weight model on the frame. Not on the screen.

The four blocks above are measured, not modelled — which is the point, and also their limit: a diff can tell you that the layout moved, but not what the decline message said. That last question needs a model, and it is where agents quietly become expensive, because the obvious implementation sends the whole screen, every frame, every time. A frontier model may well read an image better than a 4B one. That is not the question. The question is whether you can afford to ask it 29 times a session, on frames that mostly changed nothing, at full resolution. Three levers decide that, and none of them is model quality:

Cropping did not make this model cheaper, and the table above is wrong to imply that it does. Cropping to what the diff said moved — row B — cost 32,040 tokens against 32,132 for those same frames sent whole, or 99.7%, where the geometric estimate called it 48.2%. Both figures are what the model itself reported being fed (prompt_eval_count, straight from the server). Row C reaches 26,528, but that difference is the filter dropping frames, not the crop: on this stack not sending a frame pays and cropping one does not. The curve below is why — this server resizes an image up to a fixed budget before the vision encoder sees it, so a 1280×800 crop costs about the same as a whole screen. The crop still cuts the bytes on the wire, and it still points the model at what changed. It just is not a token saving here, and the only reason that is knowable is that the count was taken.

The crop is not a resize. It is the region the diff reported as changed, cut out in ffmpeg before anything is encoded or sent — so the model is never asked to ignore the rest of the screen, it is simply never shown it. That distinction is what makes a 4B model viable on a CPU: 783 tokens of screen becomes 71 tokens of the thing that actually changed. On a payment decline that is the difference between paying for a 1440×900 screenshot and paying for the error banner.

The three levers, and the models are swappableagent.py
from agent_visual_harness import Frame, OllamaBackend, LayaBackend, Triage

# every frame, whole: the baseline this section is measured against
whole = Triage(OllamaBackend("qwen3-vl:4b"), crop=False)

# skip unchanged -> Laya scores -> crop -> the VLM answers
triaged = Triage(
    OllamaBackend("qwen3-vl:4b"),  # open weights, local
    filter=LayaBackend(),                # typed, calibrated, no generation
    crop=True,
)

report = triaged.run(frames, "what did the user see go wrong?")
print(report.summary())   # includes what it declined to send

Where the open model actually wins, and where it does not. It does not win on reading a hard image — a frontier model sees more. It wins on everything around the reading. The weights are Apache-2.0, so the pipeline can be shipped and inspected rather than rented; the frame never leaves the machine, which matters when the screen contains someone's card details; the answer is deterministic at temperature 0, so a regression gate stays a gate; and because the same run holds the telemetry, an answer here can be tied back to a click at a timestamp — something no screenshot alone can do, however well it is read. 29 keyframes at 37.8% of the whole-screen price is what buys the budget to ask at all, and to escalate the two or three frames that genuinely need a bigger model. Escalation is wired and off by default: RemoteBackend is only constructed if a caller asks for it, and the report counts every frame that leaves.
